## 已确认问题

### R01 · P1 · 不同业务记录必然生成同一个对象文件名

- 位置：[sd_repository_request.cpp](../src/storage/sd_repository_request.cpp) 第 266–268 行；[domain_repository_records.cpp](../src/pregnancy/services/domain_repository_records.cpp) 第 163–164 行。
- 业务编码器把 CRC32 以小端追加到每条 payload 末尾；对象命名又计算完整 payload 的同一种 CRC32。完整合法码字的 CRC 余数相同，因此不同设置、孕期档案、体重和胎动 payload 都命名为 `2144DF1C.BIN`。
- 真实代码复现：分别编码默认设置和 `last_app=Settings`，执行初次提交及 revision 1 更新。两个 payload 不同，但文件名相同；初次提交成功，更新返回 `ObjectError(16)`，对象层为 `ExistingConflict(4)`，事务号停在 1。不是偶发哈希碰撞。
- 影响：第一个业务对象写入后，其他内容不同的记录无法保存；重新初始化卡不能从根本上解决。现有对象不可变保护避免了覆盖，但会使四应用的核心保存流程失败。
- 修复：对象身份改用不会产生该固定余数的命名方案，并提供碰撞处理；继续遵守 8.3 文件名约束，保留历史 journal 引用的兼容性。不要只给现有 CRC 增加前缀，也不要覆盖同名旧对象。
- 验证缺口：现有 repository 请求测试主要使用手工字节数组；应增加真实 domain codec → repository → 恢复的跨类型、同类型修改和多记录场景。

### R02 · P1 · 删除确认没有绑定用户确认的那张卡

- 位置：[settings_app.cpp](../src/apps/settings/settings_app.cpp) 第 476–490 行；[sd_storage_service.cpp](../src/storage/sd_storage_service.cpp) 第 2436–2459、2481–2484 行。
- 进入删除确认页时未保存 `mount_generation + dataset_id`。点击确认只重新检查当前卡的可写状态，删除 API 和排队命令也没有预期卡身份。
- 触发：在 A 卡打开删除确认页，换入已有数据集的 B 卡，待其挂载后确认。执行目标变成 B 卡的 `PREGJNL`，而确认页针对的是 A 卡。
- 修复：确认页捕获卡身份，提交和 worker 执行前分别验证；换卡使确认失效。增加 A→B 换卡确认及排队后卡变化的测试。此项由代码路径确认，未执行真实双卡删除测试。

### R03 · P1 · 休眠中止后没有恢复已经暂停的应用

- 位置：[sticky_app.cpp](../src/app/sticky_app.cpp) 第 315–335 行；例如 [weight_app.cpp](../src/apps/weight/weight_app.cpp) 第 223–224 行的 prepare-sleep 会暂停应用。
- 应用暂停成功后，RTC 读取/时间转换失败或 SD 卸载失败，协调器直接返回，没有 `resume_current()`，也没有恢复此前的 Launcher 状态。
- 影响：设备没有睡眠，但当前应用仍停在生命周期等待中，无法正常处理触摸。用户需要额外的导航动作才可能恢复；错误页也不会由已暂停的应用绘制。
- 修复：让休眠成为有明确回滚的状态转换；所有暂停后的失败出口恢复原显示所有者、输入路由和可继续操作的状态。覆盖无效 RTC、卸载失败与超时。

### R04 · P1 · 打开再关闭应用列表会丢失可继续编辑的状态

- 位置：[kick_app.cpp](../src/apps/kick/kick_app.cpp) 第 235–240 行；[weight_app.cpp](../src/apps/weight/weight_app.cpp) 第 46–49、191–194 行。
- 生命周期 checkpoint 返回既表示应用切回，也表示关闭 Launcher 或方向变化后的恢复。胎动统一跳到 Today；体重重新加载并跳到 Dashboard。
- 触发：胎动已计数但未保存，打开再关闭 Launcher，计数界面被隐藏，且没有恢复会话入口；再次 Start 会取消旧 counter。体重/基线编辑也被导航恢复流程丢弃。方向切换使用同一暂停/恢复路径，也会触发。
- 修复：区分显示所有权恢复、卡变化后的数据重载和用户取消。保持本卡上的编辑草稿及活动会话；确需丢弃时走明确的保存/取消流程。

### R05 · P1 · 部分删除失败后仍公布旧的可用恢复状态

- 位置：[sd_storage_service.cpp](../src/storage/sd_storage_service.cpp) 第 1250–1257、2498–2502 行；[sd_application_data_delete.cpp](../src/storage/sd_application_data_delete.cpp) 第 71–79 行。
- 递归删除是逐文件执行，后续 I/O、目录深度或路径错误可能发生在已有文件被删除之后。失败分支直接返回，未重新探测 manifest、失效恢复索引或通知业务缓存；外层随后重新开放请求准入。
- 影响：内存仍可能以删除前的 manifest、revision 和恢复视图处理已部分删除的数据集，请求准入与磁盘真实状态不一致。
- 修复：删除一旦开始，即使失败也必须使原恢复视图失效并重新只读探测；重建并验证前拒绝业务写入，通知所有依赖该数据集的缓存。增加第 N 个文件/目录删除失败的注入测试。

### R06 · P2 · 换卡后设备偏好没有重新加载和绑定

- 位置：[sticky_app.cpp](../src/app/sticky_app.cpp) 第 135–165、396–423 行；[sd_repository_adapter.cpp](../src/storage/sd_repository_adapter.cpp) 第 118–120 行。
- 业务应用会处理 `ready()` 失效，但协调器的设备偏好循环只 poll/save；没有随挂载代次或 dataset 变化重新 begin-load。适配器正确拒绝旧绑定，却没有上层负责恢复。
- 影响：拔插同卡或换入新卡后，语言/last-app 保存持续报 `StaleGeneration`，新卡自己的偏好也不会加载。dirty 状态下还会每个协调器循环重复提交并刷日志。
- 修复：协调器拥有偏好的卡身份状态机，先加载当前数据集并更新 desired 状态，再允许保存；永久失败不能紧密循环重试。

### R07 · P2 · 偏好请求入队即清除 dirty，异步失败后丢失重试状态

- 位置：[sticky_app.cpp](../src/app/sticky_app.cpp) 第 140–141、160–165 行。
- `begin_save()` 返回 Pending 时就清除 dirty；真正的完成结果失败时只记录日志，不恢复待保存状态，也不向用户提供明确的失败反馈。
- 影响：语言切换或 last-app 更新遇到一次异步 I/O/提交失败后，后续循环不再保存这次修改；用户需要额外操作才能重新触发。该问题独立于 R01，修复文件名后仍存在。
- 修复：把排队中、已确认保存和等待重试分别建模；使用有界退避/显式重试，并防止失败的旧快照覆盖更新的用户选择。

## 当前应用列表卡住：已观察事实与待定位部分

原始证据保存于 `dist/v1-code-review-20261010/DEVICE-HANG.log`：

- 569144 ms：协调器报告 pregnancy → settings 切换成功。
- 569177 ms：`display=refresh_begin mode=monochrome_full`，之后未出现相应 refresh-done。
- 585625 ms 起：触摸队列及 interaction 队列积满。
- 592625 ms：settings → pregnancy 的双击切换返回 `ESP_ERR_TIMEOUT`。

这支持“已切换逻辑应用，但新页面绘制停滞，屏幕仍可能显示旧 Launcher”的判断。日志没有 SPI 调用栈，不能直接宣称是某个锁死或硬件损坏。

重点待验证：

1. [epaper_panel.c](../components/seeed_epaper/epaper_panel.c) 第 481 行调用 `spi_device_transmit`。本地 ESP-IDF 5.4.1 实现对排队和完成都使用 `portMAX_DELAY`；panel 的 10 秒 BUSY 超时不覆盖 SPI 提交等待。需补充分阶段日志/任务栈取证和共享总线故障恢复，超时设计也必须保留尚未结束的 DMA/transaction 内存生命周期。
2. [sd_storage_service.cpp](../src/storage/sd_storage_service.cpp) 第 1822–1825 行的快照读取在写入中紧密自旋；writer 优先级 2，reader 应用 3、协调器 4。应测试高优先级读者同时运行时的写者进展，不能把此风险直接认定为本次根因。
3. [sticky_app_lifecycle.cpp](../src/app/sticky_app_lifecycle.cpp) 的 resume 只清请求、不等待 paused ACK 撤销。应压力测试快速恢复→再次暂停的交错，验证 coordinator 接管 Canvas 时旧 owner 确实仍处于暂停状态。
